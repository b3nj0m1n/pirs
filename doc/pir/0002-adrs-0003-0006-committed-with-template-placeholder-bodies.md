# 2. ADRs 0003-0006 committed with template placeholder bodies

> Type: Development · Severity: Low

## Problem Statement

Commit `31101b1` added ADRs 0001-0006 to the repository with `status:
accepted`, but only ADR-0001 (auto-generated by `adrs init`) and
ADR-0002 (filled by an explicit Python heredoc script) had real
content. ADRs 0003-0006 were left with the literal MADR template
placeholders (`{Describe the context...}`, `{decision driver 1}`,
`{title of option 1}`, etc.).

The omission was caught by the Copilot PR reviewer on PR #1, which
posted four near-identical review comments on those four files asking
to either fill them in or mark them as draft. The commit message at
the time falsely claimed all five ADRs had been filled, so the failure
was a combination of an actual content gap and an unverified completion
claim.

## Impact

* Documentation correctness: 4 ADRs claimed `accepted` while containing
  no actual rationale, drivers, or trade-offs — useless to anyone
  reading the repo.
* Reviewer time: PR #1 reviewer had to flag 4 separate files with
  near-identical comments and propose body content.
* Trust signal in commit messages: the previous commit message
  ("5 ADRs filled with proper MADR content") was inaccurate.
* No code/runtime impact; affected only `doc/adr/`.

## Lessons Learned

* "Generated" is not "written". Running `adrs new <title>` produces a
  file in `accepted` status with template body — it is not safe to
  commit until the body has been edited.
* When a batch of files is created in one shell session, verify each
  file individually before staging. A single representative spot-check
  (ADR-0002 here) is not sufficient.
* Commit messages should describe what was actually verified, not what
  was intended.
* Code-quality gates (`cargo build`, `cargo test`, `cargo clippy`) do
  not catch documentation-content omissions; a doc-content lint is the
  right layer for this class of mistake (see ACT-001).
